# فصل 01 — قواعد مستندسازی و حاکمیت تغییر

## اصول

1. **شواهد مقدم بر برداشت‌اند.** هر ادعای فنی مهم باید به فایل، قرارداد، تست، Commit یا Run مشخص متصل شود.
2. **وضعیت فعلی از هدف آینده جدا باشد.** طراحی پیشنهادی را به‌عنوان قابلیت پیاده‌سازی‌شده معرفی نکنید.
3. **مستندات نزدیک به کد و کتابچه هماهنگ بمانند.** راهنمای اجرایی در README یونیت و تحلیل معماری/ممیزی در این کتابچه ثبت می‌شود.
4. **هر یونیت فصل مستقل دارد.** مالکیت، ورودی/خروجی، API، وابستگی‌ها، امنیت، تست‌ها، محدودیت‌ها و معیار تکمیل باید در فصل خودش ثبت شوند.
5. **تغییرات قابل ردیابی باشند.** هر تغییر فنی مهم باید به شناسه یافته/کار، تست و Commit مرتبط باشد.
6. **اسرار ثبت نشوند.** Token، کلید خصوصی، محتوای .env و داده‌های حساس در مستندات، Log و Issue قرار نگیرند.
7. **زبان گزارش‌ها فارسی باشد.** نام فایل‌ها، شناسه‌ها، APIها و اصطلاحات فنی اصلی بدون ترجمه مبهم حفظ شوند.

## قالب ثبت یافته

برای هر یافته از شناسه پایدار مانند `AUD-SEC-001` یا `INT-E2E-001` استفاده شود و این فیلدها ثبت شوند:

- عنوان و توضیح؛
- شدت: Critical / High / Medium / Low / Info؛
- نوع: Bug / Security / Contract / Test / Documentation / Operations؛
- شواهد دقیق و Commit؛
- اثر و سناریوی بازتولید؛
- مالک یونیت؛
- اقدام اصلاحی؛
- معیار پذیرش؛
- تست رگرسیون؛
- وضعیت و Commit رفع.

## قالب فصل یونیت

هر فصل یونیت باید این سرفصل‌ها را داشته باشد:
1. هدف و مرز مسئولیت؛
2. فایل‌ها و نقاط ورود؛
3. قراردادها، API و مدل داده؛
4. جریان داده و وابستگی‌ها؛
5. پیکربندی و روش اجرا؛
6. امنیت و مدل تهدید؛
7. تست‌ها و نتایج تأییدشده؛
8. محدودیت‌ها و شکاف‌ها؛
9. برنامه اصلاح و معیار تکمیل؛
10. تاریخ/Commit آخرین بررسی.

## ثبت تصمیم معماری

هر تصمیم مهم در `handbook/decisions/` ثبت شود: مسئله، گزینه‌ها، تصمیم، پیامدها، وضعیت (proposed/accepted/superseded) و شواهد. تصمیم‌های تأییدنشده نباید به‌عنوان قرارداد نهایی معرفی شوند.

## پایان هر مرحله

هر مرحله کاری باید گزارش داشته باشد: هدف، دامنه، مسیرهای بررسی/تغییر، تست‌ها، نتیجه، ریسک باقی‌مانده، Commit/PR و گام بعدی. اگر مرحله فقط خواندنی است، باید صریحاً ثبت شود که فایل‌های کد تغییر نکرده‌اند.
